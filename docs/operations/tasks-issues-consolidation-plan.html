Tasks/Issues consolidation — decision + slice plan

Source: GitHub issue #52 · direction locked 2026-07-08 · build deferred — this document is the plan to execute against when a session picks it up, not a record of anything shipped. Canonical decision summary lives in docs/ARCHITECTURE.md — keep both in lockstep.

1 · Decision (locked)

GitHub issues are the canonical unit for anything an agent touches. The Supabase tasks table is the index / control-plane over them — fleet-only fields (tier, model, dispatch_status, auto_ok, lane, status-mirror) — not a second source of truth. Rule: agent-workable → it becomes an issue. Trivial personal reminders may stay board-only.

One surface: /ops/tasks stays the actionable board (name stays "tasks" — Adrian's preference). /ops/issues retires once cross-repo coverage is confirmed equivalent (see §3 — it already mostly is).

3 · The source_url / dispatch_url conflation

Confirmed conflated. source_url does not exist as a column or anywhere in code. dispatch_url is written from two different meanings onto the same column:

WriterWhat it stores
import-issues.mjs (importer) dispatch_url = issue.url — the imported issue's own URL (provenance).
actions.mjs#dispatch() (manual/fleet dispatch) dispatch_url = issue.html_url of a newly created @claude-mention issue (the hand-off).

Hazard: scripts/fleet-dispatch.mjs and fleet-watchdog.mjs both treat dispatch_url IS NULL as "not yet dispatched." A GitHub-imported task has dispatch_url set from the moment it's imported — it never becomes eligible for auto-dispatch, and the board can't tell "this task came from an issue" apart from "this task was already handed to Claude."

4 · Fix — pick one, then build (recommended: split fields)

OptionShapeTrade-off
A — split fields (recommended) source_url (provenance — set once by the importer, never overwritten) + dispatch_url (only ever set by an actual @claude hand-off — manual dispatch or fleet auto-dispatch). Importer stops writing dispatch_url. One migration (add source_url, backfill from existing dispatch_url on imported rows, then null out dispatch_url for rows that were never actually dispatched). Every read site (fleet-dispatch.mjs eligibility, TasksPage.tsx "dispatched" badge, watchdog re-ping) starts working correctly with zero logic changes — the column already means the right thing once the data is split.
B — collapse to one identity Single issue_url + a separate dispatch_status enum value ('imported' vs 'dispatched') to distinguish state instead of a second column. dispatch_status already exists (migration 0008) and is closer to "did the fleet hand this off" semantics already — cheaper migration (no new column), but every eligibility check has to switch from a null-check to a status-check, touching more call sites.

Either is workable; Option A is lower-risk because it's additive and doesn't change the meaning any existing code currently depends on — it only stops writing garbage into dispatch_url going forward. Adrian's call before a session builds this.

5 · Agent-ready task shape (the leverage item)

Today's tasks table has no description / acceptance_criteria / constraints columns — the dispatch body is built from title + lane/phase + deps + free-text notes (jsonb string array). To carry outcome/DoD/pointers/constraints into the @claude issue body, either:

  • add structured columns (description, acceptance_criteria, constraints — text or jsonb) and extend dispatch()'s body template to render them, or
  • reuse the existing notes jsonb with a light convention (first bullet = outcome, a DoD:-prefixed bullet = acceptance criteria) — zero migration, but unenforced shape, easy to drift.

Readiness lint (optional, cheap): before Dispatch is clickable, require title + at least one of description/acceptance-criteria to be non-empty; otherwise show "too vague to dispatch" inline instead of opening the issue. Pure function, testable like lib/tasks/tier.mjs.

7 · DoD (from the issue, unchanged)

  1. One board (/ops/tasks) shows every task/issue across all fleet repos.
  2. Each task dispatches in one click.
  3. /ops/issues retired.
  4. Provenance vs. dispatch cleanly separated (Slice 1).
  5. A documented agent-ready task template the dispatch body carries (Slice 3).
